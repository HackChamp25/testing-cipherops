Byte figures are approximate and use the draft's maximum-size formulas, the same as the Why DNSSEC needs MTL page. An SLH-DSA-SHA2-128s signature is 7,856 B and the public key 32 B (FIPS 205). A condensed signature is at most 76 B + 16 B × floor(log2 of the series length), so 124 B for the 8 to 15 leaves here. The signed ladder is the 7,856 B signature plus the rung hashes (about 8.1 KB here). A DNS answer adds about 113 B of overhead. Verification counts cover example.in only; each signed parent zone adds the same pattern. Measure exact values with the benchmark.

    
Commands follow the stock ldns, NSD and Unbound tools and the Verisign MTL forks; algorithm names and code points depend on the build, since IANA numbers for SLH-DSA-MTL are still TBD. Sources: draft-fregly-dnsop-slh-dsa-mtl-dnssec, draft-harvey-cfrg-mtl-mode, draft-kaizer-dnsop-ml-dsa-mtl-dnssec, draft-sheth-pqc-dnssec-strategy, github.com/verisign/MTL.

    
Where the standards stand (IETF Datatracker, 30 Oct 2026). MTL mode (draft-harvey-cfrg-mtl-mode-09, March 2026), SLH-DSA-MTL for DNSSEC (draft-fregly-dnsop-slh-dsa-mtl-dnssec-06, March 2026), ML-DSA-MTL for DNSSEC (draft-kaizer-dnsop-ml-dsa-mtl-dnssec-03, October 2026) and the PQC strategy for DNSSEC (draft-sheth-pqc-dnssec-strategy-02, October 2026) are individual Internet-Drafts: work in progress, not yet adopted by a working group or published as RFCs, and the first two have not been updated since March. The newest draft applies MTL to ML-DSA-44, whose signature is 2,420 B instead of 7,856 B. The strategy draft proposes running a conservative algorithm in MTL mode next to a low-impact drop-in algorithm. The workflow above should carry over to ML-DSA-MTL; the algorithm name and the sizes change.
